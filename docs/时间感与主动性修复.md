# 时间感与主动性修复

日期：2026-09-29
范围：云端大脑（`brain/brain.py`、`brain/server.py`）+ 手机端 UI（`_chat.html` / `assets/chat.html`）

---

## 一、问题清单

| 现象 | 直接表现 | 定位到的原因 |
|---|---|---|
| 反复提起已经过去的事 | 上午 6~10 点多次提到"那周末的事"，像是还没到 | 灌进上下文的历史消息不带时间标记，模型无法判断那是几小时前说的 |
| 界面看不到消息时间 | 同一天内聊几十条，一条时间都不显示 | `/api/chat` 不返回时间字段；前端仅在跨天时插入日期分隔线 |
| 历史记录只能往前翻到 29 号 | 再往前的记录取不到 | 前端固定传 `limit=60`，只取最近 60 条 |
| 凌晨收到多条消息 | 4:17 起连续收到 8 条（到 10:58，每 40 分钟一条） | 主动搭话的循环体不读取任何配置项 |

第四项是排查前三项时顺带发现的，量级比前三项都大。

---

## 二、原因分析

三处实现缺陷相互独立。

### ① 主动搭话的循环体不读配置

`server.py` 的 `_proactive_loop` 中间隔是写死的：

```python
time.sleep(2400)          # 固定 40 分钟
ans, _mode = b.chat(PROACTIVE_RULES, proactive=True, log=False)
```

`config.json` 里 `proactive` 段包含 `enabled`、`max_per_day`、`interval_sec`、
`quiet_start`、`quiet_end`，代码里一个都没读。配置中的静默时段当时写的是
`24:00~24:01`（相差 1 分钟，等同未设），但即使写对了也不会生效。

结果就是循环启动后每 40 分钟跑一轮，全天不停，按上限算一天能发 36 条。

### ② 历史消息灌回上下文时丢弃了 `t` 字段

存档 `chat_history.jsonl` 中每条都带时间（`_log_turn` 和 `_cloud_append_assistant`
都会写 `t`），但 `seed_history()` 只取了 `role` 和 `text`：

```python
# 修改前
self.hist.append({"role": role, "content": m.get("text", "")})
```

模型看到的是一排不带时间的信息，只能按"正在谈的事"来理解，于是反复重提。

### ③ 接口不返回时刻

```python
# 修改前
self._json(200, {"reply": ans, "mode": mode, "err": err})
```

前端对应 `addMsg('assistant', d.reply, '')`，第三个参数（时间）恒为空串；
且 `addMsg` 仅在跨天时插分隔线。

## 三、改动内容

### 1. 主动搭话接上配置（`server.py`）

新增 `_proactive_conf()` / `_parse_hhmm()` / `_in_quiet()` / `_proactive_used_today()` /
`_proactive_count_up()`，循环体每轮重新读取配置：

- **间隔**：读 `interval_sec`，同时把默认值从 2400 调整为 3600
- **静默时段**：读 `quiet_start` / `quiet_end`，支持跨零点（如 23:00~07:00）；
  解析失败或起止相同时按"未设置"处理 —— 宁可照常发言，也不因误判整天静默
- **每日上限**：读 `max_per_day`，计数写入 `data/proactive_quota.json`，跨天归零
- 每轮重读配置的好处是改完 `config.json` 无需重启服务

配置项调整（本地与云端两份同步）：

| 字段 | 原值 | 现值 |
|---|---|---|
| `quiet_start` | `24:00` | `23:00` |
| `quiet_end` | `24:01` | `07:00` |
| `max_per_day` | `99` | `6` |
| `interval_sec` | `2400` | `3600` |

### 2. 历史消息带时间标签（`brain.py`）

- 新增 `Brain._stamp()`，生成形如 `[09-29 11:43] ` 的前缀
- 三处进入上下文的位置统一打标签：正常对话（user / assistant 各一条）、主动搭话、
  场景搭话
- `seed_history()` 改用存档中的真实时间，产出 `[09-29 06:18] 那周末的事`
- 新增 `HIST_TIME_NOTE`（190 字），在 system 中说明标签读法。这段说明不能省：
  省略后模型会出现两种行为 —— 把方括号当正文一起模仿，或直接忽略标签、
  继续把旧消息当作当前话题
- 仅当历史中确实存在带标签的消息时才注入该段说明，避免无谓的 token 开销

### 3. 接口返回时刻 + 前端显示（`server.py` + `_chat.html` ×2）

- `/api/chat` 返回增加 `t` 字段，格式与历史接口一致（`YYYY-MM-DD HH:MM`）
- `addMsg` 的分隔线规则改为：**跨天，或距上一条超过 5 分钟**时插入，取代原来只按天插入
- 本端发送的消息用新增的 `nowStr()` 打时间；`renderHistory()` 同步重置 `lastT`
- 历史请求 `limit` 从 60 提到 300

| | 回复内容 |

## 五、手机端重新打包（v4.1 / code 14）

以下两项属于手机 App 的前端代码，必须重新打包才能生效：

| 项目 | 状态 |
|---|---|
| 每条消息显示时刻（跨天或间隔 >5 分钟插入时间线） | 已发布 |
| 历史记录 `limit` 60 → 300 | 已发布 |

安装方式：App 启动时更新提示会弹出（`/api/app/version` 返回 `code 14` > 本地 13），
确认后安装完成。

### 打包路径上的一个坑

根目录 `_zhixia.apk` 与 `deploy\app.apk` 停留在 APP_CODE 7（2026-09-21），
而设备上运行的是 code 13，两者相差 6 个版本。

若沿用轻量打包路径（`_repackage.py` 替换 assets/chat.html），产出的是
「code 7 的 Java + code 14 的 HTML」组合。code 13 新增的「模型设置页 /
错误日志页」依赖 Java 侧的 WebView 桥，而该桥不存在于 code 7 的 dex 中，
这两页在设备上会直接失效。

因此本次改用 gradle 完整构建：`.workbuddy\scripts\tools\_build14.py`（21 秒出包，
产物自带 debug 签名，证书与已安装版本一致，可直接覆盖安装）。

**判断规则**：chat.html 的新增功能一旦涉及 Java 侧（WebView 桥 / Activity），
必须走 gradle；纯 CSS / 文案改动才可以用轻量路径。

## 八、已知局限

1. **中文没有时态标记**，模型在极端情况下仍可能把过去的事说成将来。时间标签的作用
   是把信息交给模型，不替它做判断。
2. **静默时段按服务器本地时间判断**（东八区）。若服务器迁移到其他时区，该判断会随之偏移。
3. `max_per_day` 仅统计**主动搭话**，主动发起的对话不计入。
4. `_proactive_used_today()` 读不到计数文件时按 0 处理，即文件删除等于当日重新计数。
   这是有意为之 —— 宁可多发两条，也不因文件损坏导致整天静默。

# 设计与取舍

这份文档记录三件事：系统的能力构成、实现过程中踩过的坑、以及**故意没这么做**的设计选择。
README 只留架构与用法，细节和实测数据放这里。

---

## 一、能力构成

| 能力 | 实现方式 |
|---|---|
| 工具调用 | 生图（参考图锁脸，Z-Image-Turbo，4~31s）、视觉理解（VL 模型把图转成文字描述）、**语音合成（她可以发语音条）**、记忆抽取与写入、发朋友圈 |
| 语音 | **阿里云百炼 `qwen-audio-3.1-tts-flash`（2026-10-01 起）**：她写 `[voice]` 标记时合成一段 mp3 发过来。音色不是平台的预置嗓，而是**用一段参考音频零样本复刻**出来的 voice_id（目录见 `voice.VOICE_CATALOG`），App 设置页「她的声音」里可试听、可一键热切换，不用重启也不用重新打包客户端。合成失败自动降级成纯文字 —— 语音是锦上添花，不能反过来害消息发不出去 |
| 跨会话记忆 | `memory_store_v2`：bge-m3 向量检索，条目带来源与时间；`recap_store`：日→周→月三层滚动摘要，历史不会越滚越长 |
| 自主行为 | 四条循环：主动搭话（**间隔按"上次主动他理不理"自适应**，回应率低就拉长到最多 2 小时）、生活推演（30 分钟补算）、夜间写日记、朋友圈（1 小时一次，每天最多 4 条）。**做不做由她自己决定**——模型回"无"就不执行 |
| 约定的状态机 | `agenda.py` 给每条约定落状态：pending（还没到）/ done（办成了，不再念）/ missed（过期未办成，注入时明说"没办成"，**绝不允许顺延成新日子**）。状态落盘，不靠提示词约束 |
| 单步工具调用 | `tools.py`：模型写 `[tool:名:参数]`，服务端执行后把结果喂回再让她重答，**最多两轮**。三个工具：实时位置（IP）/ 天气 / 快递物流。执行用严口径（名字必须在册），**兜底清占用宽口径**（模型编的中文名字也得扫掉，不能漏给用户） |
| 关系定位 | `persona_store.relation`：人设字段里的**一段自由文本**，不枚举、不查白名单。留空退回一句默认（"认识很久的朋友，各自城市，关系好但不黏糊"）。**枚举永远补不完** —— 十年老友 / 正在追她 / 同居都不在两档里，所以整个概念从枚举退成文本。App 设置页直接编辑这段。关系段插在 `notes` 之后、身份底线之前：它是"他们现在什么关系"这个事实，而底线要压在最末尾。**必须留在 CORE_RULES 之外** —— 那里权重最高，写进去等于焊死，人设文件里写相反的话都压不过 |
| 可观测性 | `/api/chat` 每轮 + **各自治循环各一条**落 `data/trace.jsonl`：命中的记忆（含相似度）、各注入块字数、约定账本有没有带上、模型、延迟、token、是否降级，以及主动搭话**被拦掉的原因**（重复 / 自己不想说）。文件 4MB 轮转。`/api/stats` 给 App 显示"今天聊了多少轮、花了多少 token" |
| 失败处理 | 单实例互斥量、token 鉴权（空 token 只放行回环、对外绑定直接拒绝启动）、12MB 请求体上限、人设 key 白名单（防路径穿越）、静默时段、每日上限、重复内容闸门、上游失败**重试一次**（只重试网络/超时/429/5xx，401/402 不重试）、输出清洗（思考块 / 时间戳前缀）、兜底文案**不进历史与记忆** |
| 并发 | `MemoryStore` 自带可重入锁（记忆抽取是后台线程在写，请求线程同时在读），网络调用放在锁外；chat 锁**有上限地获取**（240s），拿不到就明说"在忙"而不是无限期挂住 |
| 运行形态 | 云端 7×24，三个客户端（App / 桌宠 / 直接 API）共用同一份记忆与人格 |
| 回归网 | `tests/`：134 个用例（stdlib unittest，不联网、不读真实 config、不花钱）+ GitHub Actions（跑用例 + 全仓 `compileall`） |

## 二、实现过程中踩到的坑

1. **语义检索会漏召回**：同一件事换个说法就找不回来——实测"票买了吗"（5 字）压根不进检索、"放假第一天要上班"排第 13 名召不回（只取 Top-5）。
   → 把记忆拆成三层：事实（语义检索，点状）/ 话题回顾（按时间全量带，线状）/ **约定账本 `agenda.py`（按日期强制注入，定时）**。带日期的约定不靠语义碰运气，快到那天了无论聊什么都会带上。
2. **相对时间会污染记忆**：她许诺"明天来找我"，第二天"明天"自动滑到新的一天，承诺永远兑现不了。
   → `agenda.py` 把"明天/后天/国庆/下周X/月底"按**那句话被说出的那天**解析成绝对日期，并在注入块里区分"还没到的"和"已经过完的日子（别再当约好的事提）"。
3. **自治行为会失控**：主动搭话每小时必发、凌晨连发 8 条、把刚说过的话原样再说一遍（实测 08:43/09:43、14:42/19:42、12:37/12:44 三组重复）。
   → 静默时段 + 每日上限 + **重复内容闸门**（写入前比对她最近 12 句，相同或一方是另一方的子串就跳过）+ **频率自适应**（按最近 10 次主动消息的"被回应率"伸缩间隔：≥0.5 → 不变，0.25~0.5 → ×1.5，<0.25 → ×2，上限 2 小时；他 15 分钟内说过话则这轮推迟）。
4. **相对时间会污染长期状态**：她许诺"明天来找我"，第二天"明天"自动滑到新的一天，承诺永远兑现不了（用户反馈"昨天说明天来、今天还说明天"）。
   → 两道：记忆抽取的提示词强制把"明天/后天/下周X/国庆"换算成绝对日期再入库；约定账本按**那句话被说出的那天**解析成日期并落状态，过期就标 missed、注入时明说"没办成、别顺延"。
5. **语音接口的 voice 参数是坑**：硅基流动 `/audio/speech` 的 `voice` 必须写「模型名:音色名」的完整格式（`FunAudioLLM/CosyVoice2-0.5B:diana`），只写 `diana` 会 400 `Invalid voice`。第一轮试了 20 多个音色写法全失败，才发现是这个格式问题。换成阿里后**反向又踩一次**：`qwen-audio-3.1` 的 `voice` 要填**裸的 voice_id**，加了模型名前缀反而失败。
6. **"标称 48kHz"骗了我们一整轮**：硅基和阿里的文档都写支持 48kHz，我据此判断"换平台能救高频"。用**无损 WAV 逐段看频谱**才证伪——两家的 48k 都只是**容器 48k、内容 24k**，13kHz 以上是 -90dB 的空白；逐段相比，阿里那条 48k 与它自己的 24k 输出几乎完全重合（差 0.1~0.3dB）。
   → 教训两条：**不能用 mp3 测高频**（编码器自己的噪声会混进指标里，看着很热闹）；**标称采样率不等于有效带宽**。真要比就比 8~13kHz 那段的能量差——阿里（-13.9dB）比硅基（-30.7dB）高约 17dB，这段是齿音和句尾余音，听感差别是实的，但**两者都不是真 48k**。
7. **配置文件里有一层"隐形的拷贝"**：`server.py` 启动时把 config 的几个段拷成 `API_CFG` 再传给各模块（`voice.synth()` 拿到的就是它）。这个拷贝**漏过两次**——2026-09-28 漏了 `vision`，2026-10-01 加语音时又漏了 `voice`。症状是"配置文件改了、实际一点没生效"，而且因为代码里的默认值碰巧和配置一致，能瞒很久。
   → App 一键换声音必须**同时改 `api_config`（落盘）和 `API_CFG`（内存）**，只改一处就是"看着换了、声音还是旧的"。这跟 2026-09-22 人设热重载踩的是同一个坑：**内存里那份才是运行时真正读的**。

## 二半、可观测性：一行 trace 解决"她为什么这么答"

排查只能靠 SSH 上服务器 grep 日志，是这套系统之前最大的短板 —— "她没想起 25 号的票"到底是**没召回到**还是**召回了没用上**，全凭猜。

现在每轮落一行 `data/trace.jsonl`（只记结构化中间数据，不记模型内心活动）：

```json
{"t":"2026-10-01 17:20","kind":"chat","in_len":12,
 "blocks":{"persona":512,"memory":180,"life":430,"agenda":96,"rules":1180,"total":3210},
 "mem_hits":2,"mem_top":[0.71,0.64],"agenda":1,
 "model":"zai-org/GLM-5.3","ms":1620,"tok_in":3210,"tok_out":74,"fallback":0}
```

它同时解决了成本问题：以前余额耗尽只能等她开始说"脑子转不动"才发现（2026-10-01 真实事故），现在 `/api/stats` 直接给出今日轮数、token、平均延迟、降级次数，App 设置页就能看。

## 三、设计取舍

- **没有用 Agent 框架（LangChain 等），编排是手写的**。云主机只有 2C2G，依赖轻、启动快、出问题时能直接看自己的代码栈；代价是轮子自己造，编排逻辑散在 `server.py` 的几个循环里。
- **图片不把像素喂给主模型**，先用 VL 转成一句话描述再进上下文。省 token、可控（描述里可以明写"没看清"），VL 挂了也能降级成"看不到"，不会让主对话崩。
- **记忆抽取与向量化放后台线程**，不阻塞回复。用户感知的是回复延迟，不是记忆写入延迟。
- **主动消息不做"每轮必发"**，她自己决定（回"无"就不发）。真人不会每小时都主动找人——宁可少发，也不要刷屏。
- **工具调用用手写标签，而不是原生 function calling**。当时只有 3 个工具、一次一个、最多两轮，标签够用，也不依赖服务商的 `tools` 实现；代价是拿不到并行调用、参数 schema 校验和生态（MCP）那套。**要扩到十个以上工具，这个选择就该反过来。**
- **约定账本的日期解析取"白名单 + 宁可漏不可猜"**。用大模型解析日期更灵活，但错误率高且不可复现；正则白名单解析不出来就不进账本 —— 漏一条约定无害，编错一个日期会把"已经过去的日子"说成还没到。

## 四、实测数据

| 项目 | 结果 |
|---|---|
| 主模型端到端延迟对比（5 个模型，相同负载） | GLM-5.3 ≈1.6s / DeepSeek-V4-Flash ≈2.0s / Qwen3-30B-A3B ≈3.4s / Qwen3.8-27B 43s（带思考，弃用）→ 选 GLM-5.3 |
| 主动消息重复率 | 加去重闸门前后：08:43 与 09:43、14:42 与 19:42 等重复组 → 0 |
| 上游欠费（HTTP 402） | 降级为固定兜底文案，并跳过记忆与日记写入，避免把"脑子转不动"当成她说过的话记进记忆 |
| 语音有效带宽（无损 WAV 逐段频谱，2026-10-01） | 阿里 Qwen-Audio-3.1 **10.8kHz**（8-11k -13.9dB / 11-13k -31.9dB）｜硅基 CosyVoice2-0.5B **7.7kHz**（-31.5 / -45.8）→ 8~13k 段相差约 **17dB**，选阿里；两家 13kHz 以上均为 -90dB 空白，**谁都不是真 48k** |
| 语音月成本（每天 10 条 × 约 33 汉字） | 阿里 Qwen-Audio-3.1 按 token ≈ **¥0.37/月**（实测音频约 12.5 tok/s，每条 ≈¥0.0012）｜硅基 CosyVoice2-0.5B 按 UTF-8 字节 ≈ ¥1.48/月 |
| 单日对话条数的上限（暴露 `pending_rows` 那个 bug） | 单日 600 条时，旧逻辑把 **576 条一次性**喂给一次压缩，而正文被截到 8000 字 → 后面的内容从没被压过、水位线却推过去了（永久跳过）。现在硬切 240 条/批、跨轮次补齐，实测跨 3 轮覆盖完整 |
| 回归网（2026-10-03） | `tests/` **134 个用例**，`python -m unittest discover -s tests -t tests` 约 0.25s 跑完（不联网、不读真实 config、不花钱）。新增当天就靠它抓出 2 个真 bug（见上一条与"标签泄露"） |

## 五、已知不足

- **仍然没有多步规划**：现在是"组装上下文 → 一次 LLM 调用（+ 最多两轮单步工具）"，不是 plan-then-act。工具链编排、多轮规划、评测集这三块还没碰，是下一步的方向。
- **约定一致性已经落成状态机**（pending / done / missed，见 `agenda.py`），不再是提示词约束。仍然靠规则的部分是日期解析：只认白名单里的说法，"过两天""下周有空的时候"这类模糊表达进不了账本 —— 宁可漏，不可猜。
- **没有 LLM 行为的自动化评测**：`tests/` 罩的是**纯逻辑与接口契约**（日期解析、水位线、索引一致性与并发、静默时段、重复闸门、标签清扫、鉴权判定、两份 chat.html 一致……），**不是**"她答得好不好"。她说得自不自然、有没有编细节，仍然只能靠真实使用观察。补这个需要一套带断言的口语用例 + 固定模型，是下一步最该做的事。
- **刻意没做的三件事**（不是漏了）：
  1. **`print` 换 `logging`**：86 处调用点、跨 29 个模块，而现在只有纯逻辑有测试网 —— 在测试覆盖面到得了那些路径之前不动它。现状是日志打到 stdout，**重启就没了**。
  2. **SSE 流式输出**：能把首字延迟从约 1.6s 压到几百毫秒，但它是**新增能力**而不是修 bug，而且客户端要一起改（`chat.html` 的假打字、`PollService` 的 30 秒轮询），需要真机回归。
  3. **Dockerfile**：服务端目前是 Windows-only（单实例守卫走 `ctypes.windll.kernel32.CreateMutexW`，另有几处 `C:\linzhixia\...` 兜底路径）。写一个没在 Linux 上跑过的 Dockerfile，正好犯了这个仓库这轮在修的毛病 —— **声称比实际多**。要做就做完并验证。
- **`PollService` 没有停止入口**：前台服务起来之后用户关不掉它（只能去系统设置里强停），而且 `POST_NOTIFICATIONS` 被拒时通知会被静默吞掉。
- **TLS 仍然是缺的**：服务端是纯 HTTP，所以 Android 侧 `usesCleartextTraffic="true"` 收不掉；要收掉得先给服务端上 HTTPS。
- **鉴权只做到"共享 token"这一层**：没有 TLS、没有限流、没有访问日志（`log_message` 是刻意关掉的，否则日志会淹掉磁盘）。token 仍可从 `?token=` 传（媒体请求没法带头），所以它还是可能出现 URL 里。
